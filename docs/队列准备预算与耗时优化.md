# 队列准备预算与耗时优化（2026-11-26）

## 问题与原因
用户截图选25组、最多调用20，初始无历史时关联上界为24次（首组本地初始化）。旧前端先创建/上传整个会话，再请求后端preview才提示预算不足；错误只写聊天提示，底部队列区仍像在等待，容易被误认为卡住。

## 修改
- 在point-sampling.js新增无副作用inspectQueue，复用现有脚本资源，不新增需重启的后端静态白名单。
- 准备前检查新增完整组数、首组条件、授权上限及现有会话剩余预算。预算不足/输入无效不上传创建会话、不请求preview、不调用模型，不自动提高上限。
- 25组/20次立即显示“最多需要24次”，并保持原预算20。旧会话剩余上限不足时单独提示，不暗中扩大会话授权；可以减少选点或新会话重用原文件。
- 队列区直接显示预算提示和准备结果，不要求用户到聊天底部找错误。
- 准备阶段显示“检查选择与预算→创建免费会话并保存原始观测→后端校验队列及调用预算”，每400毫秒刷新用时；完成/失败后停止计时。
- 每次准备清除旧预览和费用勾选；完成仍需重新授权。请求超时沿用现有30秒上限，不自动重试。前端只是提示，后端继续权威校验。

## 测试
三个用户(2).zip共966条观测，抽25组。独立TestClient三次创建会话142.3～147.53ms，正确preview22.02～24.77ms，预算不足preview28.93～31.01ms；模型调用0。此为进程内隔离HTTP耗时，不含浏览器/网络/磁盘环境差异，不是生产SLA。

浏览器真实导入三包：上限20时前端拒绝、创建请求0/preview请求0/派发0；修改24后创建1次、preview1次、仍未调用模型。人为延迟免费preview650ms验证阶段提示和重复点击禁用；完成画面约0.86秒，含测试延迟，不是自然耗时。

后端逐组/API/架构范围44项通过；Node预检、既有抽样/双阵分组/字段去重四组通过。浏览器空间候选、缩放拖动、刷新回归通过，回归只用假网关。真实模型调用0。
