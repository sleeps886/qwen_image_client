# 轨迹生成模块：边界、契约与解耦设计

更新日期：2026-11-26  
用途：指导模块独立维护、替换和迁移，减少页面、模型服务、定位算法和绘图之间的耦合。

> 本文基于当前工作区代码编写，包含尚未提交的代码现状。**现状**与**建议方案**分别标注；文档本身不会完成代码解耦。本次不修改业务代码、不调用付费模型。

## 1. 范围与目标

截图对应“图片识别”入口。本文中的轨迹生成模块指：接收识别结果或观测数据，完成轨迹校验/定位，生成轨迹文档与图片。

包含：
- 图片识别后的轨迹 JSON 校验和绘图。
- 双阵观测的空间定位、连续估计、重投影检查与候选轨迹输出。
- 与 HTTP、SSE、模型网关、历史结果存储的交接边界。

不包含：
- `/generator` 中本机 `btr_gens` 仿真工具的内部生成算法。当前仓库只负责其页面嵌入与启动，不能据此推断该外部项目的实现。
- 增量预测、实时跟踪、三类图融合的完整内部设计。它们应作为独立工作流接入公共契约，不能直接混入此模块。
- 真值评测、图片相似度评分、密钥管理、云端计费。

解耦目标：替换模型不改绘图；替换绘图库不改定位；调整 HTTP/SSE 不改算法；新增工作流不通过渲染函数中的条件分支实现。

### 2.1 当前主要数据流

```text
页面 → recognition 路由 → 输入准备 → SonarAgent → ModelGateway
                                         ↓ 模型完整输出
  普通路径：parse_tracks → render_document
  双阵路径：关联/身份复核 → 定位 → 连续估计 → 重投影 → render_document
                                         ↓
                           tracks.json + PNG + 诊断文件
                                         ↓
                              HTTP/SSE 结果 → 页面
```

注意：旧兼容入口 `render_tracks` 在 `context.require_spatial` 为真时会调用 `solve_spatial`，并非始终是纯绘图函数。Agent 的证据路径会在完成跟踪后调用 `render_document`，不能把两条路径当成同一种输入。

## 3. 必须保留的接口契约（现状）

### 3.1 轨迹 JSON

普通模型轨迹由 `parse_tracks(answer, context=None)` 校验。最小方位—时间示例：

```json
{
  "coordinate_system": "bearing_time",
  "position_observable": false,
  "warnings": ["仅方位—时间，不表示地理位置"],
  "tracks": [
    {
      "id": "T1",
      "branch": "main",
      "points": [
        {"t": 0, "x": 30, "y": 0},
        {"t": 5, "x": 32, "y": 5}
      ]
    }
  ]
}
```

| 字段/约束 | 当前规则 |
|---|---|
| coordinate_system | local_xy_m、lon_lat、bearing_time 三选一 |
| t | 秒，有限数值，同一轨迹内严格递增；从 0 到 context.T_MAX，未提供时上限为 604800 秒 |
| local_xy_m | x 为东向米、y 为北向米；绝对值不超过 1e7；坐标参考须随结果说明 |
| lon_lat | x 为经度 [-180,180]，y 为纬度 [-90,90] |
| bearing_time | x 为折叠舷角 [0,180] 度，y 必须等于 t；存在图像标定时还检查标定角度范围 |
| 空间轨迹前提 | 图片模式需 platforms，且原文 position_observable 必须为 true；数据模式有单独规则 |
| tracks | 1～100 条；id 为 1～80 字符；branch 默认为 main，长度不超过 80 |
| points | 图片模式每条 2～2000 点；数据模式每条 1～2000 点；总计不超过 20000 点 |
| warnings | 至多 100 条字符串，每条至多 2000 字符 |

空间前提检查只是格式/输入门槛，**不是位置可观性的物理证明**。空轨迹不会被补造成成功结果。

数据模式还校验坐标系、对象/分支/点数及数值是否被模型改写；meta 重建路径可以将验证后的模型采样替换为完整 source_tracks。双阵观测 JSON 应先经关联与定位处理，不能直接按普通轨迹 JSON 解释。

### 3.2 绘图接口

```python
parse_tracks(answer, context=None) -> dict
render_tracks(answer, directory, context=None) -> dict
render_document(doc, directory, context=None,
                *, filename="estimated_track.png", persist=True) -> dict
```

- `render_tracks`：旧适配入口，负责解析或求解后再绘图，不宜成为新模块的公共核心接口。
- `render_document`：接收已校验/已求解的文档，不重新定位；使用 Matplotlib Agg 和进程内绘图锁。
- 默认写出 `estimated_track.png`；`persist=True` 时写出 `tracks.json`。输出目录由调用方准备。
- 当前渲染器会添加坐标参考、绘图摘要等字段，存在修改传入 doc 的行为；迁移前不能假设它是无副作用纯函数。
- 当前实现的部分分支会直接访问 `context.get`，接入方应传字典（至少 `{}`），不能仅凭默认参数假定所有场景均支持 None。

### 3.3 HTTP 与流式边界

- `POST /api/recognize`：支持 `dry_run=true`，只校验不调用模型。
- `POST /api/recognize/stream`：SSE；真实发送须确认 `consent`，不等同于 dry-run。
- 常用表单字段：files、platform、prompt、input_mode、renderer_profile；同步入口另有 dry_run。
- 模型连接参数由后端配置，拒绝请求覆盖 model/base_url/api_key 等字段。
- 页面依赖 result_id、answer、usage、downloads、trajectory_image、trajectory_status、warnings 等结果字段。
- 状态区分 `not_generated`、`bearing_time`、`position_estimate`；HTTP 成功或 ok=true 不代表已生成轨迹图。
- 流式分片只用于展示，完整模型输出结束后才校验/绘图；不能对半截 JSON 出图。
- SSE 还存在阶段、正文/推理片段、节点、心跳、result/error 等事件；迁移时以路由和前端消费代码为准做兼容测试，不能随意重命名。

## 4. 耦合点与拆分办法

| 现状证据 | 问题 | 建议改法 |
|---|---|---|
| render_tracks 内动态导入 solve_spatial | 绘图入口承担定位选择 | 新编排层显式选择算法，渲染器只接轨迹文档；旧函数保留为兼容外壳 |
| SonarAgent.render 中包含复核、跟踪、文件写入、出图 | render 名称掩盖完整业务流程 | 拆出生成用例与制品持久化；Agent 仅协调 |
| recognition 路由自行组合下载、状态和部分错误信息 | 同步/流式结果易漂移 | 共用结果映射器；SSE 只包装事件，不重复业务判断 |
| context 字典跨输入、定位、渲染传递 | 隐式字段和流程开关扩散 | 按用途拆分 Calibration、PlatformContext、RenderOptions，边界做类型校验 |
| 网关收 output_root 并返回 output_dir | 模型调用与文件存储绑定 | 后续新增“模型输出 DTO + ArtifactStore”适配；保留原网关接口过渡 |
| render_document 修改 doc 并落盘 | 计算、显示和存储混合 | 核心文档不可变，渲染返回图片/元信息；统一由存储端口提交 |
| 前端基于文件名/元数据识别结果类型 | 展示与制品实现细节绑定 | 后续增加显式 result_kind/capabilities，兼容期保留旧字段 |

现有正确边界应保留：输入校验不依赖绘图/定位；服务与模型不依赖 FastAPI；ModelGateway 可替换；HTTP 通过依赖注入创建工作流。

## 5. 目标结构（建议，尚未实现）

不为解耦而立即拆微服务。优先在现有 Python 工程内形成清晰边界：

```text
HTTP / SSE / CLI 适配器
         ↓
TrajectoryUseCase（用例编排）
         ├── 输入策略：普通轨迹 / 双阵观测 / 用户数据
         ├── ModelPort（可选）
         ├── 关联、定位、连续估计、质检
         ├── TrajectoryDocument（统一输出）
         ├── RendererPort
         └── ArtifactStorePort
```

依赖规则：
1. 核心契约只使用普通类型/领域对象，不包含 UploadFile、Request、StreamingResponse、密钥或页面 DOM。
2. 定位算法不调用模型、不启动 HTTP 服务、不渲染图片；质检也不能隐式改写定位结果。
3. 渲染器不得导入定位服务、模型网关或 API 路由；从模型原文到轨迹文档的转换在用例层之前/之中显式完成。
4. 存储端口集中处理目录、文件名白名单、原子提交与清理；算法不读取项目 outputs 全局目录。
5. 用例发出领域进度事件，HTTP 适配器再转成 SSE；回调失败不应篡改算法结果。
6. 依赖由组合根注入，禁止以共享可变 Agent 单例承载不同请求的状态。

建议的公共概念（不是现有 API）：

| 对象/端口 | 应承载 | 不应承载 |
|---|---|---|
| GenerationInput | 输入类型、观测/轨迹、标定、平台和显式策略 | HTTP 请求对象、密钥 |
| TrajectoryDocument | 坐标系、时间单位、参考原点、身份/分支、点和警告 | PNG URL、模型连接配置 |
| GenerationResult | 状态、文档、诊断、来源和制品引用 | FastAPI Response |
| RendererPort | 已校验文档 + 显示选项 → 图片制品 | 模型原文、定位求解 |
| ArtifactStorePort | 一次运行的创建、提交、查询与清理 | 轨迹生成和模型推理 |

新增契约版本应与现有 HTTP `schema_version=1.0` 区分；不能未经迁移就把文档版本视作接口版本。扩展身份、镜像、断段、来源与质检字段时，保留其语义，不以一条平滑线替代不确定性。

## 6. 渐进迁移与验收

### 阶段一：先锁定行为
- 固定普通轨迹、方位—时间、用户数据、双阵候选、失败无图五类测试夹具。
- 记录现有 JSON/SSE 与文件契约，保留结果 URL 和历史读取行为。
- 使用假网关验证，不调用真实模型。原始回复保留，解析失败不造图、不自动付费重试。

### 阶段二：拆用例而不改接口
- 从 SonarAgent.render 提取生成用例，把证据复核与普通轨迹解析作为显式策略。
- HTTP/SSE 复用同一业务结果及映射器；旧方法继续委托新实现。
- 将大 context 拆为明确对象，在旧入口集中转换，避免全项目同时改字段。

### 阶段三：分离绘图和存储
- 所有定位先完成再进渲染器；移除新路径对 render_tracks 定位分支的依赖。
- 保护输入文档不被渲染修改，文件写入由存储适配器统一提交；PNG/JSON 不完整时不发布成功链接。
- 当前 PLOT_LOCK 仅进程内有效；若未来多进程运行，应采用唯一运行目录并设计并发提交，不能把该锁当分布式锁。

### 阶段四：独立复用
- 在不启动 FastAPI、不读真实密钥、不访问网络的测试中，从固定输入生成 JSON/PNG。
- 更换假网关不修改渲染；更换假渲染器不修改定位；更换临时存储不修改算法。
- 通过架构测试阻止反向依赖；保持现有入口兼容后，再考虑是否独立打包。

验收底线：JSON 中点位、身份与镜像语义不变；空间与方位图不混淆；失败时保留诊断但不伪装成功；历史结果仍可读；密钥不进入文档、事件或制品。
